# Live 끼어들기 재생 중단·재개 제어

상태: completed (전화 없는 구현·검증 범위). 위 계획 제시 뒤 사용자가 “진행해줘.”라고 승인했다.
실제 발신 없이 API·합성 입력과 회귀 검증을 진행한다.

## 확인된 문제

한국어 지시와 음성 공급 여유분은 적용됐지만, 사용자가 끼어들 때 로컬/회선 출력 중단은
연결돼 있지 않다. 사용자는 본인 음성을 듣기는 하나 도우미가 말을 이어간다고 확인했다.
실통화 음성은 저장하지 않아 그 통화의 파형으로 모델/회선 지연을 소급 분리할 수 없다.
음성 공급 공백 감소와 끼어들기 제어는 별도의 성공 기준이다.

공식 근거: https://developers.openai.com/api/docs/guides/voice-server-controls?api=live
출력은 앱/중계에서 mute/drop하고 큐를 비우며 교정 지시를 보낼 수 있다. 명령 ACK는
재생 재개 신호가 아니다. 폐기한 음성도 모델 문맥에는 남으므로 재개 문맥을 검증해야 한다.
Realtime의 response.cancel/truncate를 Live에 그대로 보내지 않는다.

## 권장 범위

1. 전화 없는 실 API 합성 음성으로 끼어들기 시작/모델 발성/전송/모사 재생/전사/ACK의
   시간을 분리 기록한다. 현행이 말을 계속하는 사례부터 재현한다.
2. 기존 LiveBridge에 독립적인 중단 상태를 추가한다. 지속 발화를 판별하는 음성 감지와
   Live 자체 전사의 명시적 중단·정정 표현을 비교한다. 외부 STT/TTS 모델은 추가하지 않는다.
   짧은 맞장구·잡음·에코를 모두 중단으로 처리하는 단순 음량 1회 감지는 채택하지 않는다.
3. 중단 판정 시 로컬 큐/이미 대기 중인 회선 음성을 clear하고, 이후 들어오는 과거 응답
   음성을 일시 폐기한다. 입력은 계속 모델에 보내고 앱이 작성한 짧은 양보 지시를 전달한다.
   음성 중계 스레드에서 지시 ACK를 기다리지 않도록 한다.
4. 상대의 발화 종료와 이전 출력의 정지를 확인한 뒤 새 응답을 재개한다. ACK 하나 또는
   고정 타이머 하나만으로 재개하지 않는다. 오래된 문장 재생, 새 답변 첫음절 손실,
   무한 음소거를 회귀 사례로 다룬다. 모델 문맥에 남은 미청취 응답을 정정 지시로 보완한다.
   재개 경계를 신뢰할 수 없으면 제한을 보고하고 자동으로 운영 기본값에 적용하지 않는다.
5. 취소된 종료 대기·위임 결과·playback ACK와 계측을 함께 정리한다. 폐기된 음성은
   실제 전달/청취된 것으로 보고하지 않는다. marin/선택한 말투와 음성 공급 보완은 유지한다.

## 검증과 완료 기준

- 실패 테스트 → 중단/clear/뒤늦은 음성/재개/종료 회귀 테스트 → 실제 Live 합성 음성 비교.
- 일반 발화 중 정정, “잠시만요”, 짧은 “네”, 잡음/에코, 연속 두 번의 끼어들기,
  인사 중 재발화, 명령 실패/지연을 검사한다.
- 중단 감지 이후 모사 회선에 새 발성 패킷을 보내지 않는지, 보류 음성이 clear되는지,
  상대 발화 종료 뒤 최신 조건으로 답하는지 각각 검증한다.
- 입력 시작부터 실제 중단까지의 지연과 오탐을 보고한다. 목표는 통제된 입력에서
  500ms 이내 재생 중단이며, 실회선 지연 보장이나 달성된 수치로 미리 표현하지 않는다.
- 고정 타이머로 잠깐 숨긴 뒤 이전 답변을 계속하는 결과는 성공이 아니다.
- API 시험 음성과 결과를 로컬 비교 페이지에 제공한다. 실제 전화는 이 단계에 포함하지
  않고 결과 확인 뒤 별도 1회 검증한다. Google 접근/제품 UI 변경은 없다.

예상 파일: calls/live_bridge.py, 필요 시 별도 interruption.py, 관련 회귀 테스트,
scripts/check_live_korean.py와 음성 계측, 계획/로드맵. 원본 음성·전사는 ignored var에만 둔다.
검증 통과 후에만 적용하고 관련 코드·검증 기록을 로컬 Git에 커밋한다.

## 구현 결과

- 로컬 WebRTC VAD(webrtcvad-wheels 2.0.14)와 320ms 발화 누적을 사용한다. 전화 PCM을
  외부 STT에 보내지 않는다. 최근 출력 파형과 높은 상관이 있는 입력은 에코 후보로 제외한다.
  이 검사는 범용 에코 제거가 아니며 시간 정렬이 다른 실제 스피커폰 에코에는 제한이 있다.
- 도우미가 이미 말할 때의 새 지속 발화만 중단한다. 상대의 기존 발화 중 도우미의 맞장구는
  새로운 끼어들기로 취급하지 않는다. 짧은 입력/잡음 판정과 출력 재개 상태를 별도 관리한다.
- clear로 로컬/회선 대기를 비우고 수신 중인 이전 출력을 폐기하며, 새 상대 입력과 전사는
  계속 받는다. 교정 지시 ACK를 기다리는 작업은 음성 수신과 분리했다.
- 상대 발화 600ms 정지, 모델 저음량 패킷 240ms 이상과 최근 수신/발성 시각, 교정 지시 ACK를
  함께 확인한 뒤 재생을 연다. 추가 재개 명령은 새 응답을 끊는 사례가 있어 최종 구현에서
  제거했다. 발화 종료 뒤 새 발언에 답하도록 최초 중단 지시에서 안내한다.
- 명령 실패/ACK 제한 또는 입력이 멎은 뒤 12초간 복구 불가이면 명시적 오류로 회선을
  정리한다. 무한 음소거하거나 오래된 음성을 시간만 보고 재생하지 않는다.
- 끼어들기 전 백엔드 결과/종료 판단과 대기 질문은 적용하지 않는다. ACK 대기 사이에 발생한
  끼어들기도 재확인한다. 이전 재생 ACK는 폐기하고 미확인 음성을 나중 ACK로 되살리지 않는다.
- 기존 웹 진행 표시의 계산만 함께 수정해 폐기 음성을 계속 전송 중/재생 완료로 표시하지
  않게 했다. 레이아웃 변경은 없다. barge_in_started/resumed와 폐기량은 로컬 DB에 기록한다.
  이 새 이벤트의 Langfuse 전용 전달은 이번 변경에 추가하지 않았다.

## 검증 결과

- 기존 실제 API 대조(barge-baseline): 정정 입력 중 발성이 2776ms 겹쳤다.
- 최종 단일 정정(barge-final): clear 381ms, 겹침 294ms. 전사는 “시간은 오후 여섯 시입니다”.
- 연속 정정(barge-repeat): clear 382ms/300ms, 마지막 전사는 “오후 일곱 시입니다”.
- 대기/재개(barge-pause): clear 361ms. 대기 안내 뒤 조용히 기다리고 계속 요청에 날짜/시간 응답.
- 짧은 맞장구(barge-backchannel, 264ms 입력): clear 0회, 폐기 0바이트.
- 최종 방식의 정상 정정·연속·대기 기록에서 hold 구간에 발성 패킷 전송 0개.
  실제 API는 Live를 사용했지만 입력은 Yuna 합성, 회선/ACK 및 위임 결과는 모사다.
- 실험 중 0.84초 중단/재개 후 무응답, 재개 명령으로 응답이 짧게 잘리는 후보는 채택하지 않았다.
  기존 실험 도구의 미지원 session.context.append도 위임 발생 시 오류로 드러나
  문서화된 session.thinking.append로 수정했다. 실패 실행은 성공 통계에서 제외한다.
- 새 회귀: 중단·수신 계속·ACK/무음 분리·복구 타임아웃·맞장구·저음량 잡음·정렬된 에코·
  폐기 재생 집계·오래된 위임 결과/질문·결과 ACK 경합. 통화 테스트 217개 통과.
  웹 테스트 33개, Ruff/ESLint/TypeScript/웹 빌드 통과.
- 활성 회선/실행 중 채팅 0건을 확인하고 기존 dev 실행기를 재시작해 반영했다.
  선택한 marin과 기본 한국어 지시 및 공급 공백 보완은 유지했다. 실제 발신·Google 작업 없음.

검증 자료는 ignored var/korean-live-lab/barge-*에 있다.
http://127.0.0.1:9122/barge-in.html 에 입력+출력 시간축 비교 음성을 제공한다.
예전 max_queue_ms 계산은 폐기량을 대기로 오인하므로 새 실행부터 실제 큐 길이로 계측한다.
playback_silence_latency_ms는 전송된 저음량 패킷의 시각이며 gate의 무음 시간과 다르다.
중단은 clear_latency_ms와 hold 구간의 패킷 부재를 기준으로 평가한다.

## 남은 제한

실회선 clear 수행 시간·스피커폰 에코·다양한 발화 길이/소음은 미검증이다. 파형 상관은
제한된 에코 후보 제거이며 실제 화자 분리나 의미 이해가 아니다. 길게 늘인 맞장구는 오탐할 수 있다.
출력의 quiet 구간은 명시적인 응답 ID 경계가 아니므로 매우 빠른 응답·발화 중 긴 쉼에서
새 응답 누락/조기 재개 가능성을 추가 평가해야 한다. API 합성 시험 통과를 실통화 보장으로
표현하지 않는다. 실제 청취 자연스러움과 자동 종료는 다음 승인된 실통화에서 확인한다.
