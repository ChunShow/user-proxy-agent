# 브라우저 통화 듣기 실회선 검증

상태: completed (실회선 청취·조작 검증). 승인: 본인 번호 1회 통화로 양쪽 음성·듣기 켜기/끄기와 회선 유지를
검증하자는 제안에 사용자가 “좋아 진행해줘.”라고 승인했다.

## 범위

기존 본인 번호에 웹 새 대화로 한 번만 발신한다. AI 청취 테스트임을 알리고 짧은 일상
질문으로 대화한 뒤 상대가 종료를 요청하면 인사 한 번 후 종료하도록 한다.
Google 작업·추가 발신·녹음 저장은 포함하지 않는다. 모델/음성 설정도 유지한다.

## 절차와 완료 기준

1. 서버/활성 회선/공급자 사전 점검과 기존 듣기 관련 검사를 확인한다.
2. 연결 후 웹 통화 듣기를 켜고 연결 상태와 실시간 전사를 확인한다.
3. 듣기 중지 후 회선이 유지되는지 확인하고 다시 켠다.
4. 통화 종료 후 청취가 해제되고 결과 카드가 복원되는지 확인한다.
5. 양쪽 음성의 실제 청취·지연/끊김은 사용자 피드백으로 확인한다. 화면의 연결 상태만으로
   실제 음성 품질이 검증됐다고 하지 않는다. 결과/제한을 문서·로드맵에 기록하고 로컬 커밋한다.

대상: 기존 CallListening/callAudio, 읽기 전용 listen WebSocket과 AudioHub.
예상 변경은 검증 문서·로드맵이며 기능 변경이 필요하면 원인과 수정 범위를 먼저 정한다.

## 결과

- 서버 health 정상, 활성 회선 0건, 공급자 접근/발신번호 idle/Live 제어 연결 사전 점검 통과.
  backend 듣기 검사 3개와 웹 μ-law 디코딩 검사 1개 통과.
- 본인 번호로 웹에서 1회 발신했다. 통화 중 듣기 클릭 후 연결 상태가 표시되고 양쪽 전사가
  갱신됐다. 듣기 중지 뒤 웹과 DB에서 connected/stop_requested=0을 확인했다.
  다시 듣기를 켜자 연결 상태가 복구됐다.
- 사용자는 컴퓨터 브라우저에서 본인과 도우미의 음성이 “양쪽 모두 잘 들렸어요”라고 확인했다.
  숫자로 측정한 종단 지연이나 모든 환경의 음질을 보장하는 결과는 아니다.
- 사용자는 마지막에 직접 전화를 끊었다고 확인했다. 서버의 audio_drained와 carrier completed를
  자동 종료 성공으로 해석하지 않는다. 이번 회선에는 별도 carrier_hangup_requested가 없었다.
- 종료 뒤 듣기/종료 버튼이 제거되고 결과가 표시됐다. 새로고침 뒤 같은 종료 카드와 보고가
  복원됐다. 추가 발신·Google 작업·음성 저장은 없고 제품 코드는 변경하지 않았다.

## 후속 관찰

통화 모델은 일상 질문 대신 일반적인 도움 안내로 대화했고, 마지막 종료 사유가
recipient_declined로 분류돼 화면에는 “통화를 거절”로 표시됐다. 일반적인 종료 요청과
통화 거절의 구분, 재생 확인과 실제 종료 주체의 표현은 다음 종료 기록/결과 표시 단위에서
검토한다. 자동 결과 보고는 이 대화의 사용자 청취 피드백을 알지 못하므로 그 보고의
청취 미확인은 이번 외부 검증 결과와 구분한다.
