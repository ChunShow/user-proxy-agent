# 2단계: 채팅 화면 디자인 Implementation Plan

> **For agentic workers:** Execute inline by default. Steps use checkbox (`- [ ]`) syntax.
> 이 프로젝트에서는 병렬 작업에 별도 합의가 필요하며, 이번 단계는 직접 순차 실행한다.

**Goal:** 사용자가 비서에게 메시지를 보내고 통화 진행 상황을 살펴보는 경험을,
실제 발신 없이 조작 가능한 웹 화면으로 검토한다.

**Architecture:** 기존 React 웹에 채팅과 통화 카드 컴포넌트를 만든다.
화면 상태는 메모리에서 관리하고, 예시 통화 데이터와 화면 컴포넌트를 분리한다.
기존 health API와 연결 검사는 유지하며 실제 채팅·통화 API는 이번 단계에서 추가하지 않는다.

**Tech Stack:** 기존 React·TypeScript·Vite·CSS. 브라우저 회귀 검증에
`@playwright/test`를 개발 의존성으로 추가하고 버전은 설치 시 lockfile에 고정한다.

**Spec:** [제품 방향과 구조](../../product.md), 이 문서의 ‘화면·동작 제안’.

## Global Constraints

- 메인 에이전트와의 입력·응답은 텍스트 채팅이다.
- 웹부터 반응형으로 구현하고, 이후 앱이 같은 서버 API를 사용할 수 있도록 한다.
- 업무 상태와 통화 상태는 별도로 관리한다. 통화가 정상 종료되어도 업무가 미완료일 수 있다.
- 이미 위임된 범위는 진행하고 새 결정이 필요하면 사용자에게 질문한다.
- 이번 단계는 화면 검토용이다. 모델·전화·Calendar·Gmail 요청과 사용자 데이터 영속 저장은 없다.
- 형제 프로젝트와 backend API 계약을 변경하지 않는다. 1단계의 health·재시도 동작을 유지한다.
- 화면 설계와 구현에 지정된 `frontend-design` 스킬을 적용한다.
- 승인 후 작업 단위별 검증·로컬 커밋을 남긴다. 다음 단계의 구현은 별도 컨펌 대상이다.

## 접근 방식 비교

| 방식 | 장점 | 한계 |
| --- | --- | --- |
| **채팅 안 통화 카드 + 펼치는 상세 내역 (추천)** | 대화 맥락 유지, 좁은 화면에도 자연스러움 | 긴 전사는 별도 펼침이 필요함 |
| 채팅과 통화 패널을 항상 나란히 표시 | 통화 정보를 한눈에 확인 | 일반 대화에도 공간을 차지하고 모바일 구조가 달라짐 |
| 통화 화면으로 전환 | 통화 정보에 집중 | 추가 지시를 위해 채팅과 화면을 오가게 됨 |

첫 번째 방식으로 제안한다. 통화 상세도 같은 카드에서 펼쳐 단일 대화 흐름을 유지한다.

## 화면·동작 제안

### 레이아웃과 디자인

이 화면의 사용자는 일을 맡기고 진행을 확인하는 개인이다. 첫 행동은 메시지 작성이다.
데스크톱은 접을 수 있는 좁은 탐색 영역과 최대 760px의 대화 영역으로 구성한다.
탐색 영역에는 메인 대화와 화면 예시 진입만 둔다. 저장되지 않은 과거 대화 목록을 꾸며 넣지 않는다.
모바일에서는 탐색 영역을 메뉴로 접고 대화와 입력창을 우선한다.

```text
데스크톱
┌────────────┬──────────────────────────────────┐
│ Agent      │ 내 비서                 서버 상태 │
│ 메인 대화  │                                  │
│ 화면 예시  │         사용자 메시지             │
│            │ 비서 메시지                      │
│            │ ┌ 통화 카드 ───────────────────┐ │
│            │ │ 목적 / 업무 상태              │ │
│            │ │ 상대 / 통화 상태              │ │
│            │ │ 내역 보기 · 듣기 · 통화 종료   │ │
│            │ └─────────────────────────────┘ │
│            │ [ 메시지 입력                 ↑ ] │
└────────────┴──────────────────────────────────┘

모바일: 상단 메뉴 → 대화와 통화 카드 → 하단 입력창
```

- 밝은 단일 테마로 시작한다. 배경 `#F6F8FC`, 표면 `#FFFFFF`, 본문 `#172435`,
  보조 `#526176`, 진행·포커스 `#166B61`, 실패·종료 동작 `#B33D46`을 토큰으로 둔다.
  테두리와 연한 채움은 이 색들의 투명도·혼합으로 파생한다.
- 제목·작은 브랜드는 `Avenir Next`와 한국어 시스템 글꼴, 메시지는 `Apple SD Gothic Neo` /
  `Malgun Gothic` / sans-serif, 시간·전화 정보는 ui-monospace를 사용한다.
  기본 메시지 16px, 줄 높이 1.65, 보조 13px, 시작 제목 28–32px. 외부 폰트 요청은 없다.
- 사용자 메시지는 오른쪽 진한 본문색 바탕·흰 글자, 비서 메시지는 왼쪽의 연한 중립색
  말풍선으로 구분한다. 상단에 비서 이름과 작은 연결 표시를 두고 하단 입력창은 모서리를
  둥글게 한다. 좁은 말풍선에 긴 글을 가두지 않는다.
- 특징은 **대화 사이에서 펼쳐지는 통화 카드**다. 목적과 업무 상태를 첫 줄에,
  회선 상태를 별도 줄에 두어 ‘끊김’과 ‘목표 달성’을 다르게 읽을 수 있게 한다.
- 색상만으로 상태를 전달하지 않는다. 동작 버튼은 텍스트 이름을 가지며, 장식용 파형과
  실제 음성처럼 보이는 애니메이션은 넣지 않는다. reduced-motion 설정을 존중한다.

디자인 자체 점검: 큰 환영 영역과 여러 기능 홍보 카드는 제거한다. 첫 입력을 바로 할 수 있게
하고, 시각적 강조는 진행 중인 통화 카드 한 곳에 집중한다.

### 채팅 입력과 화면 예시

- 기본 `/`는 빈 메인 대화와 입력창이다. ‘화면 미리보기 · 메시지는 저장되지 않습니다’와
  ‘아직 비서가 연결되지 않았습니다’를 짧게 표시한다.
- 입력한 메시지는 브라우저 메모리에만 추가한다. 버튼 이름은 ‘메시지 추가’로 두고,
  서버로 전송했다고 표시하거나 임의의 비서 응답을 생성하지 않는다.
- 공백만 있는 입력은 추가하지 않는다. Enter는 추가, Shift+Enter는 줄바꿈,
  한글 IME 조합 중 Enter는 추가하지 않는다. 추가 후 입력창의 초점은 유지한다.
- `/?preview=call`은 고정된 예시 대화와 통화 카드다. 예시 선택은 이 화면에서만 노출한다.
  자유 입력으로 가짜 시나리오를 추론하거나 자동 재생하지 않는다.
- 예시 상단에는 ‘예시 데이터 · 실제 전화가 연결되지 않습니다’를 항상 표시한다.
  새로고침 시 사용자 입력·조작은 초기화한다. 예시 이동 시 작성 중인 초안은 메모리에 유지한다.
- 예시 대화의 상대는 ‘예시 병원’으로 표시한다. 실제 병원의 진료 시간이나 실제 사용자의
  전화번호·녹음·기록을 예시 데이터에 사용하지 않는다.

### 통화 카드의 표시와 개입

예시 선택: `연결 중`, `통화 중`, `추가 확인 필요`, `목표 달성`, `종료했지만 미완료`, `연결 실패`.
화면 상태는 프론트엔드 검토용이며 이후 서버 이벤트 계약으로 확정한 것이 아니다.

| 항목 | 이번 단계 동작 |
| --- | --- |
| 목적·진행 요약 | 할 일과 확인된 범위를 짧게 표시 |
| 통화 내역 | 카드 안에서 펼침·접기, 비서와 상대 발화 및 부분·확정 상태 표시 |
| 듣기 | 연결된 예시에서만 로컬 on/off 전환, ‘듣기 켜짐 (예시)’ 표시. 실제 오디오 재생 없음 |
| 추가 지시 | 해당 카드의 지시 대상 표시와 함께 입력창으로 초점 이동. 추가한 글은 ‘지시 예시’로만 표시 |
| 통화 종료 | 즉시 로컬 `ending`으로 변경. 예시 도구의 ‘종료 확인’을 눌러야 `ended`로 전환 |
| 종료 후 결과 | 종료 조작만으로 업무를 성공 처리하지 않는다. 해당 예시의 확인 결과를 유지 |

통화 카드 조작 중에도 일반 메시지 작성은 가능하다. 사용자 직접 음성 참여, DTMF 수동 입력,
실제 종료 요청·음성 구독·지시 전달은 이번 단계 범위가 아니다.

## Task 3: 반응형·접근성 검토와 인계

- [ ] 1440×900, 768×1024, 390×844, 320×568에서 빈 대화·긴 대화·통화·실패 화면을 확인한다.
  긴 한국어·영문·URL 때문에 가로 넘침이 발생하지 않고 입력창이 마지막 메시지를 가리지 않아야 한다.

  통화 내역 펼침은 `aria-expanded`, 상태 변화는 필요한 짧은 영역에만 `aria-live`를 적용한다.

  브라우저 viewport로 검증한 범위임을 기록한다.
- [ ] 검증 결과와 화면을 사용자에게 제시하고 문서를 갱신한다.
  `docs: record chat design verification`로 커밋한다. 3단계는 별도 계획·컨펌 후 진행한다.
