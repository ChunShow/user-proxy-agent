# 통화 승인 카드 생성의 대화 문맥 처리

상태: complete

승인: 계획 제시 직후 사용자가 “수정하고 검증해줘.”라고 요청했다.

## 요청과 확인 결과

사용자가 통화 기능을 작은 단위로 정교화하면서 승인 카드 생성의 반복 오류를 확인해 달라고 요청했다.
최근 대화에는 전화 예약 요청 → 이름/날짜 확인 질문 → 사용자 답변 → 카드 생성 실패가 반복된다.

`CallManager._register`는 `requested_number`로 마지막 사용자 메시지에 전화 지시 정규식이
일치하는지 확인한다. 번호는 이전 사용자 메시지에서도 찾지만 요청 의도는 마지막 한 문장만
검사한다. 도구는 거부 결과를 `call_request_required`, `retry_automatically: false`로 반환한다.
챗봇은 이를 일반 오류/재요청 안내로 바꾸어 사용자가 같은 요청을 반복하게 된다.

격리된 임시 DB, 실제 도구 래퍼, 가짜 통화 공급자로 다음을 재현했다. 실제 발신은 모두 0회다.

| 마지막 입력(앞서 번호와 전화 요청 존재) | 결과 |
| --- | --- |
| 내일 | call_request_required |
| 김테스트 | call_request_required |
| 다시 해줘 | call_request_required |
| 사용자 제공 번호 + 로 걸어줘 | call_request_required |
| 다시 전화해 | call_request_required |
| 전화해줘 | awaiting_approval |

현재 검사에는 첫 요청부터 모든 조건이 있는 경우와 금지 문구 사례가 있으나,
확인 질문에 답한 뒤 승인 카드를 만드는 다중 턴 사례가 빠져 있다.

## 제안하는 수정 범위

1. 카드 제안과 실제 발신 권한을 구분한다. 마지막 문장의 전화 명령어 일치를 카드 생성의
   필수 조건으로 사용하지 않는다. 메인 에이전트가 현재 대화의 전화 요청과 확인 답변을
   해석하여 완성된 카드만 제안하도록 프롬프트/도구 설명을 명확히 한다.
2. 서버는 같은 소유자·대화의 사용자 메시지에 실제로 존재하는 번호인지 검증한다.
   모델이 지어낸 번호, 외부 데이터의 번호만으로는 카드를 만들지 않는다.
3. 사용자 취소·단순 문의에는 카드를 제안하지 않도록 대화 평가를 추가한다.
   과거 요청을 무조건 재개하는 방식으로 구현하지 않는다.
4. 실제 발신은 기존 소유자·버전·만료·카드 버튼 승인과 원자적 claim으로 계속 보호한다.
   사용자 답변이나 채팅의 “다시”만으로 승인/발신하지 않는다.
5. 오류 응답은 카드 작성 실패와 실제 발신 실패를 구분하고, 같은 말을 반복 요청하는
   안내를 없앤다. 기존 통화가 있으면 확인하고 무조건 새 카드를 만들지 않는다.

## 파일과 검증

- `calls/manager.py`, `calls/tools.py`, `chat/prompts.py`와 관련 테스트를 최소 수정한다.
- 도구 통합 검사: 전화 요청 → 이름 또는 날짜 답변 → 카드 1개 생성, 발신 0회.
- 부정 사례: 추측 번호, 다른 소유자, 취소/단순 문의, 오래된 대화의 별개 요청,
  기존 카드 중복 생성, 중복 승인·취소·만료 후 발신 금지.
- 실제 메인 모델에 합성 다중 턴 대화를 입력해 도구 결과와 카드 내용을 확인한다.
  전화 공급자는 가짜 구현으로 막고 실제 전화/Google 쓰기를 실행하지 않는다.
- 웹에서 카드 표시·새로고침·승인 전 발신 0회를 확인한다.
- 승인된 범위의 회귀 검사 후 활성 통화가 없을 때 서비스에 반영하고 로컬 커밋한다.

## 완료 기준

사용자가 이미 전화 요청과 번호를 제공했다면 이름·날짜만 답해도 같은 업무의 승인 카드가
생성된다. 카드 없이 발신하지 않고, 승인 버튼 전 외부 통화 작업은 0회다. 실제 모바일에서의
발신/음성 평가는 이번 카드 수정과 별도로 진행한다.

## 완료 결과

- 마지막 문장에 전화 명령어를 요구하는 검사를 제거했다. 번호 근거·소유권 검사는 유지하고
  명시적인 전화 금지와 번호 누락은 서로 다른 오류로 반환한다.
- 프롬프트와 도구 설명에 후속 답변·취소·별개 업무·기존 카드 처리 기준을 명시했다.
- 카드 오류에는 단계, 발신하지 않았다는 사실, 부족한 정보/기존 카드 확인 안내를 추가했다.
- 새 도구 검사 8개가 기존 코드에서 실패하는 것을 확인한 후 수정했다.
- backend 348개, Ruff, 실제 메인 모델 합성 10개, 공유 웹의 이름 답변 → 카드 생성 →
  새로고침 복원 → 취소를 확인했다. [평가 기록](../../evaluations/2026-09-28-call-card-context.md).
- DB 백업 후 활성 통화·채팅이 없는 상태에서 로컬 서버에 반영했다. 공유 주소는 유지했다.
- 실제 전화는 걸지 않았다. 대화 의도 분류는 메인 모델의 판단이며, 모든 문맥의 정확성을
  보장하지 않는다. 실행 권한은 기존 승인 버튼과 서버 승인 검사가 담당한다.
