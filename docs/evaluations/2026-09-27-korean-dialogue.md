# 한국어 다중 발화 음성 평가

## 목적과 방법

실제 전화 없이 Yuna 합성 한국어 음성을 20ms PCMU 패킷으로 gpt-live-1/marin에 넣었다.
음성 응답과 전사를 받으며 실제 프로덕션 LiveBridge와 DeepAgents 메인 모델을 사용했다.
DB는 실행별로 격리하고 전화망/재생 ACK를 모사했다. Google/통신사 클라이언트는 만들지 않았다.
모델에 텍스트로 “종료 도구를 호출하라”고 시험한 것이 아니라, 실제 음성 대화를 통해
판단과 도구 호출이 일어나도록 했다. 종료 승인 직후 새 음성을 넣는 별도 사례도 추가했다.

통화 시작 후 모델 응답을 기다려 다음 합성 음성을 넣었다. 20초 동안 응답이 없어서 강제로
다음 입력을 넣은 경우, 입력 전사 누락, API 오류, 남은 입력이 있는 조기 종료는 평가 제한이다.
전사만 존재한다고 적절한 답을 했다는 뜻은 아니므로 각 발화를 별도로 읽어 검토했다.
합성 입력과 소수 반복이며, 실제 사람의 청감이나 실제 회선 종료의 성공률은 측정하지 않았다.

## 프롬프트 비교: 30세션

5개 사례를 설정별 2회씩 실행했다. `baseline-repair`는 baseline의 제보 문구 재현 2회이며,
나머지 8회는 `baseline`이다. 모든 결과를 포함하고 불리한 실행을 제외해 성공률을 만들지 않았다.

| 설정 | 전체 | 입력·전송·응답 대기 검사 통과 | 평가 제한 | 주요 내용 문제 |
| --- | ---: | ---: | --- | --- |
| 기존 baseline | 10 | 8 | 거절 1회 입력 전사 누락/응답 대기 초과, 1회 live_content_filter | 장황한 복창, 대기 멘트, 인사 반복 |
| 짧게 재구성 candidate | 10 | 8 | 활동 문의/거절 각 1회 시작 응답 대기 초과 | 활동 세부 설명 요구, 시간/선호 재확인, “그만 말할게요”처럼 어색한 수습 |
| 기존 바탕 candidate-v2 | 10 | 8 | 거절 2회 live_content_filter | 기억 확인 질문에 이전 이유 설명, 불필요한 확인 멘트와 복창 |

위의 숫자는 대화 품질 합격 수가 아니다. 평가 제한 없이 실행된 대화에도 내용 실패가 있었다.
`live_content_filter`는 실제 API 오류 코드이며 차단 원인/필터 정책은 이 평가에서 확인하지 않았다.

제보된 “이유를 묻자 원래 활동 질문을 그대로 반복”하는 현상은 baseline의 관련 4회에서
재현되지 않았다. baseline에서도 간헐적이라는 점을 확인했으며, 이 소수 실행으로 문제가
없거나 수정안이 해결했다고 결론 내릴 수 없다. 두 수정안은 채택하지 않는다.

## 발견한 제어 결함

candidate-v2/activity_reason-1의 상대 음성은 “제가 방금 뭐 하고 있다고 했죠?”였지만,
이전의 전화 이유 설명과 인사가 재생됐다. 기록에서 다음 순서를 확인했다.

1. 21.9초: backend가 만든 이전 이유 설명/인사를 Live에 종료 안내로 전달.
2. 22.86초: 상대의 새로운 질문 음성 시작.
3. 서버는 `ending`을 취소했지만 모델의 이전 종료 지시는 갱신하지 않았음.

이는 원 제보의 무위임 재질문과는 다른 문제다. 서버의 종료 취소와 모델 대화 상태가 달라져
후속 대화에 영향을 주는 결함으로 판단했다. 입력 루프를 막지 않는 별도 작업으로 재생 대기를
비우고 모델에 종료 취소/최신 발언 처리/종료 재판단을 전달한다. 최신 종료 결정과 직렬화하고
새 결정이 있으면 오래된 취소 작업이 이를 덮어쓰지 않는다.

## 제어 수정 검증: 추가 4세션

기존 baseline 프롬프트를 유지하고 수정된 bridge로 시험했다. 종료 승인 뒤 기억 확인 질문을
넣은 `farewell_followup` 2회는 모두 `end_canceled`와 `end_resume_completed`가 기록됐고,
컴퓨터를 하고 있다는 답을 되짚은 뒤 다시 종료 판단을 받았다. 종료는 모사 재생 ACK 기준이다.
활동→이유→기억 확인 2회 중 1회는 입력·전송 검사를 통과했으며, 다른 1회는 시작 응답이
20초를 넘어 강제 입력이 발생했다. 후자의 결과를 정상 대화 성공으로 계산하지 않는다.
확인된 제어 결함을 수정한 근거이며, 원 제보의 질문 반복을 해결했다는 근거는 아니다.

총 34회 실제 API 세션을 실행했다. 관련 자동 검사 229개와 Ruff 검사를 통과했다.
종료 취소 명령의 ACK를 기다리는 동안에도 다음 음성을 수신하는지, 오래된 취소가 새로운
종료 결정을 덮어쓰지 않는지를 회귀 검사로 확인했다. 두 프롬프트 수정안은 적용하지 않았다.
응답 지연, 어색한 확인/인사, 일부 API 차단은 여전히 남아 있다.
진행 중인 작업/통화가 없는 것을 확인하고 로컬 서버를 재시작해 제어 수정만 반영했다.
백엔드 상태 확인과 웹 페이지 모두 HTTP 200으로 응답했다.

## 파일과 재실행

- 실행법: [평가 CLI 안내](../../scripts/fixtures/live-dialogue/README.md)
- 사례: [live_dialogue_cases.py](../../scripts/live_dialogue_cases.py)
- 원본 출력: ignored `var/live-dialogue/<label>/<case>-<repeat>/result.json`
- 입력/모델 원출력/모사 재생/합친 음성: 같은 디렉터리의 WAV 파일
- 프롬프트 원문과 hash, 백엔드 입력/결과, 실제 API 이벤트를 함께 보존했다.
- 청취 페이지: http://127.0.0.1:9123/ — 34개 합성 대화 음성과 전사를 비교한다.
  로컬 서버는 `var/live-dialogue/listen`의 HTML/WAV만 제공하며 원본 DB는 노출하지 않는다.

평가 도구와 결과 기록은 완료했으나, 전체 대화 품질 문제의 해결을 선언하지 않는다.
다음 구조 개선은 확인된 답/남은 질문/최신 질문을 명시적으로 관리하면서 응답 지연도 함께
측정하는 방향이 필요하다. 모든 발언을 무조건 백엔드에 위임하거나 금지 문구를 계속 추가하는
방식은 이번 결과만으로 채택하지 않는다.
